Technical protocol spec

Marketplace Protocol Core

A draft v0.2 state machine, object registry, and event surface for agent-mediated Pokemon card transactions where intent, trust, evidence, route risk, escrow, settlement, and reputation stay typed.

Draft v0.2 Agent-neutral Pokemon alpha Escrowed intent Measured trust

Scope

What the protocol must do.

The alpha coordinates buyer agents, seller agents, verifiers, arbiters, escrow contracts, carriers, and external trust sources for Pokemon single-card trades. It does not require one marketplace, one database, one agent, one chain, or one trust score.

Represent intent

Capture what the buyer wants, what they will pay, what risks they accept, and when the agent must ask.

Expose inventory

Let sellers reveal listed and hidden Pokemon cards under access, attention, pricing, and evidence policies.

Measure trust

Accept arbitrary proof chains, preserve source and scope, and let buyer agents weight them.

Lock commitments

Bind funds, seller bond, route terms, evidence duties, inspection windows, and release gates.

Resolve outcomes

Turn clean closes into receipts and failures into claim packets, disputes, refunds, or bond actions.

Harden over time

Record outcomes so agents learn which proofs predict clean trades in which apertures.

Card reference

The database names the print. It does not testify for the card.

Pokemon alpha needs database access for search, autocomplete, card images, set metadata, and variant narrowing. The reference row is a catalog candidate only: useful for identity language, never enough for possession, condition, authenticity, price truth, or route lock.

Use it for

Known print, set, number, rarity, language, variant, catalog image, and source coverage.

Not proof of

Seller possession, physical authenticity, card condition, seller inventory, price truth, or language claim.

Gap path

If Japanese vintage coverage is incomplete, agents create a manual database-gap packet instead of pretending the source disproves the card.

Identity and signatures

Every authority claim needs a key.

Agent-neutral does not mean identity-neutral. A protocol object is only signed if the actor identifier resolves to a public key and the payload has a canonical signing form.

Primitive Rule Why It Matters
Actor ID Use stable IDs such as did:market:buyer:..., did:market:seller:..., did:market:verifier:..., or chain-native addresses. Every agent, seller, verifier, arbiter, and attester must resolve to a signing authority.
Public key Actor registry records active keys, revoked keys, role, service URL, and controller. Signatures must be verifiable after a dispute opens.
Signature form Objects are signed over canonical JSON with sorted keys, explicit schema version, object id, and trade id when applicable. Prevents replay, ambiguous payloads, and "I signed something else" disputes.
Delegation Humans can delegate bounded authority to agents with limits, expiry, revocation, and human-interrupt conditions. Agent actions need proof they stayed inside mandate.
Revocation Registries expose key revocation, agent deauthorization, verifier suspension, and arbiter suspension events. Trust sources and signatures cannot be permanent when control changes.

Matching surface

Discovery is explicit: registry, query, or brokered proposal.

A match is not magic produced by a value map. v0.2 supports three disclosure modes so buyers and sellers can choose how public their intent or inventory should be.

Mode How It Works Required Candidate Fields
Intent registry Buyer agent publishes funded intent; seller agents submit candidate inventory against the intent. intent_id, proposer, inventory_claim, price, trust_offer, route_options, expiry.
Inventory query Buyer agent queries a seller access policy or seller agent directly. query_id, seller, access_policy, disclosed_fields, attention_cost, candidate_claims.
Brokered proposal A marketplace, verifier, shop, or agent broker proposes a candidate and signs provenance. broker_id, provenance, fees, conflicts, candidate_claim, buyer_visible_terms.

Actors

Roles are explicit and composable.

One party may play multiple roles, but the protocol should record which role made each claim, accepted each risk, or signed each outcome.

Actor Responsibilities Authority Limits
Buyer Sets mandate, budget, risk tolerance, attention policy, and final acceptance authority. Can delegate bounded actions but must approve irreversible exceptions.
Buyer Agent Matches intent, weighs proofs, asks questions, negotiates terms, recommends action. Cannot waive human gates outside mandate.
Seller Provides inventory, price, evidence, route promise, bond, and truth claims. Cannot change locked route or evidence duties without buyer-side acceptance.
Seller Agent Surfaces inventory, protects seller attention, answers buyer probes, negotiates trust offer. Must respect reserve, floor, privacy, and evidence policies.
Verifier Signs condition, authenticity, custody, shop, account, or evidence attestations. Authority is limited to the claim and method signed; verifier must disclose conflicts and cannot share beneficial ownership with seller for the same trade.
Escrow Contract Locks funds, bonds, release gates, timeouts, and payout/refund actions. Executes typed terms; does not decide ambiguous facts alone.
Arbiter Resolves disputes from packets of promised, happened, and accepted facts. Must be registry-listed before escrow lock; bound by arbitration terms, fee schedule, and covered promise scope.
Arbiter Agent Ingests case packets, checks conflicts, requests missing evidence, drafts findings, and prepares ruling packets. Can act only inside signed ArbiterAgentDelegation; high-value, fraud, authenticity, or contradictory evidence escalates.
Automated Arbiter Applies pre-agreed evidence checks and remedy schedules for low-value, low-ambiguity disputes. Must be selected before escrow lock and must stop at signed friction thresholds.
Attester Signs observations from external sources such as marketplaces, shops, or domains. Does not endorse the seller; only signs observed claims.

Registries

External authority is discoverable and revocable.

The alpha does not need a large governance system, but it does need registries for actors whose signatures can move money or settle disputes. Registry entries are protocol data, not vibes.

VerifierRegistry verifier_id, categories, methods, fee_schedule, independence_policy, dispute_history, status. Lets agents decide whether a verifier has authority for this claim and trade category.
ArbiterRegistry arbiter_id, covered_case_types, value_bands, fee_schedule, response_window, appeal_policy, profile_hash, public_key, status. Lets agents discover active arbiters, verify signed profiles, and avoid an undefined approved panel.
AttesterRegistry attester_id, source_adapters, methods, rate_limits, revocation_path, audit_log. Defines who can sign marketplace, shop, domain, route, or account-control observations.
EscrowRegistry escrow_id, custody_model, supported_assets, release_api, dispute_hold_policy, legal_entity, status. Makes the money layer explicit before funds or bonds lock.

Contact legibility

The protocol does not claim jurisdiction over physical truth. It records accountable contact: who or what touched a source, object, route, gate, claim, or ruling; under which role and limits; what that contact may be used for; and what it does not prove. API calls, carrier lookups, catalog references, shop proofs, photos, inspections, and rulings become contact receipts before they can inform agents or spend at gates.

Trust system

Proofs carry scoped authority, not universal trust.

Sellers can attach any proof. Buyer agents probe each proof and weight it from the buyer's aperture. Weighting may vary by agent, but v0.2 requires the agent to disclose which proofs it accepted, discounted, rejected, and why.

Weighting is disclosed, not universal

The protocol does not impose one reputation algorithm. It requires a buyer-agent decision trace so two agents can disagree without hiding the reason.

  • accepted_proofs: trusted for this trade.
  • discounted_proofs: useful but stale, weak, or out of scope.
  • rejected_proofs: unsigned, unbound, revoked, challenged, or irrelevant.
  • remaining_risks: what still needs escrow, bond, evidence, or a human answer.

Proofs bind to this trade

A proof used to move money must include the current trade id or a challenge nonce generated for this trade. Unbound proofs may inform discovery, but they cannot satisfy a release gate.

Private predicates

Some facts should be proven as predicates rather than published as raw data or collapsed into a scalar. A seller can prove that an outside-marketplace account satisfies a buyer's threshold without exposing the whole account history. A buyer can prove funding capacity without revealing their hard cap.

ZK-ready, not ZK-required

The alpha path accepts signed predicate attestations from registered attesters or verifiers, but escrow can now require the predicate hash to pass a registry-approved verifier contract before anchoring it. The local harness uses a stub; the packet shape already reserves circuit identifiers, verifying-key hashes, public inputs, and proof bytes for a production ZK verifier.

Proof Field Meaning Required Rule
trade_id or challenge_nonce Binding between proof and this transaction or this verification challenge. Required for any proof satisfying escrow, route, condition, or trust gates.
source Where the evidence comes from: marketplace, shop, verifier, wallet, route, protocol receipt. Must be preserved and visible to buyer agents.
issuer Who signed or observed the proof. Must be challengeable or reputation-bearing.
subject Seller, shop, account, item, route, or prior trade the proof is about. Must match the current seller, item, route, or declared scope.
claim The narrow thing asserted: account control, shop existence, condition, route acceptance. Must not be broadened by downstream agents.
method OAuth, domain nonce, API read, verifier inspection, signed handoff, photo hash. Determines strength and failure modes.
freshness When the proof was observed and when it expires. Stale proofs must be refreshed, discounted in the trace, or rejected.
scope Category, object, route, location, value band, or account context. Agents weight proofs only inside their scope.
outcomes Clean closes, disputes, claims, bond hits, verifier mismatches. Update future authority without flattening to one score.

Escrow and bond

Money locks behind typed promises.

Escrow is the settlement rail. Bond is the seller's economic accountability. Both need exact gates, exclusions, timeouts, and dispute paths before the buyer commits. Every trade must disclose whether escrow is custodial, on-chain, hybrid, or simulated.

Escrow model disclosure

  • Custodial: legal entity holds funds and exposes release API.
  • On-chain: contract locks assets and evaluates signed gate events.
  • Hybrid: off-chain facts with on-chain settlement or bond custody.
  • Simulated: no real money movement; only valid for tests.

Bond adequacy

  • Bond amount is shown as currency and fraction of item value.
  • Uncovered value gap is displayed before escrow lock.
  • Covered promises and exclusions are signed in EscrowTerms.
  • Partial failure can map to partial bond action or refund.
  • Frivolous dispute cost can be posted by the disputing party.
Release Gate Signal Authority Object / Event Conflict Rule
escrow_funded Escrow service or contract. EscrowLocked. If funding confirmation fails, trade cannot enter EvidencePending.
seller_bond_locked Escrow service, bond contract, or approved custodian. BondLocked. If required bond is missing or under-disclosed, buyer must approve gap.
evidence_accepted Buyer agent, verifier, or human depending on mandate. EvidenceAccepted or HumanResponseReceived. Rejected evidence returns to EvidencePending or opens a human gate.
route_committed Seller agent plus carrier/verifier/shop evidence where applicable. RouteCommitted. Route mutation requires RouteChangeRequested and buyer-side acceptance.
delivery_confirmed Carrier, verifier, shop, local handoff memo, or buyer confirmation. ReceiptConfirmed. Conflicting delivery signals keep funds locked and open ClaimOrDisputePending.
inspection_closed Buyer, buyer agent inside mandate, verifier, or timeout rule. BuyerAccepted, ClaimOpened, DisputeOpened, or WindowExpired. WindowExpired settles only if no open exception or unresolved human gate exists.

Evidence

Evidence scales by value, trust gap, route, and condition risk.

The protocol should avoid ritual proof for low-risk trades while producing complete claim packets for high-risk endings.

Evidence Class Examples Used For
Item evidence Photos, scans, video, flaws, serials, provenance, verifier notes. Condition acceptance, misdescription disputes, resale packet.
Trust evidence Marketplace attestation, shop proof, domain nonce, bond, prior receipts. Seller access, buyer confidence, agent recommendation.
Route evidence Label, tracking, insurance, packaging proof, signature, handoff memo. Insurance claims, lost package, local handoff disputes.
Settlement evidence Escrow receipt, release event, refund event, bond action, final receipt. Accounting, reputation, arbitration, provenance.
Attention evidence Paid evidence request, seller response hash, deadline, credit-back terms, satisfaction trigger. Extra photos, holds, prep work, seller payout, buyer credit, no-show accounting.

Buyer clarity

Extra seller work is priced before the buyer asks for it: full credit, partial credit, no credit, waived fee, or deposit.

Seller respect

The seller agent can protect its human's time, price preparation work, and avoid unpaid inventory holds.

Protocol boundary

The protocol can enforce fee terms and hashes. It cannot judge whether a photo is good enough unless a quality rule or signed reviewer says so.

Verifier scope

"Verified" is not a protocol state.

A verifier stamp must carry the exact claim it supports. The protocol should never let packet completeness, cert correlation, seller custody, route readiness, or claim readiness blur into a generic "verified item" label.

No scope laundering

A verifier can be active, buyer-approved, and still only authoritative over one narrow claim.

Scope travels with display

Agents may summarize, but the summary must retain checked scopes, excluded scopes, freshness, and challenge options.

Value map decides sufficiency

The same attestation may be enough for one buyer, weak for another, and irrelevant to a different route or claim.

The local EVM harness now makes this a hard gate. A registered verifier cannot attach loose evidence to a trade. The buyer first signs a VerifierScopeApproval, then the verifier commits a VerifierScopeAttestation bound to an already anchored subject hash, the approved scope-set hash, and a method-id hash.

Scope What It Can Say What It Must Not Imply
packet_completeness Required fields and evidence refs are present. The evidence content is true.
seller_custody The seller likely controlled the item at capture time. The seller still controls it later.
raw_card_identity Photos plausibly identify the raw card described. The card is authentic or exact-grade.
graded_cert_correlation Visible slab or cert evidence correlates with a grading-company record. The slab cannot be fake, swapped, or stale.
route_readiness Carrier, local handoff, verifier-forwarding, or insurance duties are ready. The item itself is as described.
insurance_claim_readiness Packet is sufficient to begin a carrier or insurer claim. The claim will be approved.
private_predicate_threshold A private fact passed a registered predicate. The hidden evidence should be treated as public proof.

Arbitration

Arbiter selection is part of the deal, not a last-minute admin choice.

Agents should know which arbiters exist before funds lock, then choose by scope, value band, evidence burden, speed, fee, conflicts, and past outcomes. The arbiter is accountable; their agent can be the clerk, packet reader, evidence requester, and draft writer. For low-cost mechanical cases, the selected arbiter can be a registered automated policy that stops at signed friction thresholds.

Discovery

Registry proves active authority. Signed profiles describe scope, fees, evidence rules, conflicts, and delegation.

Availability

For a real trade, agents request short-lived quotes: fee, SLA, value ceiling, evidence floor, and conflict disclosures.

Selection

Buyer and seller agents converge on a selected arbiter plus acceptable backups before escrow locks.

Delegation

An arbiter-run agent may triage, request evidence, and draft rulings, but bounded authority and escalation rules are signed.

Automation

Low-cost, low-ambiguity cases can use an automated arbiter until money, ambiguity, trust risk, or attention crosses a threshold.

Friction threshold rule

The protocol may automate matching, evidence review, route checks, low-value remedies, and bounded arbitration until a typed threshold is crossed. Thresholds include money at risk, remedy severity, evidence ambiguity, trust gap, privacy exposure, conflict risk, and human attention cost.

Automate the obvious

Automated arbiters are for cases where the terms, evidence packet, and remedy schedule are already clear. They must emit replayable ruling packets and escalate when the next decision has meaningful cost, ambiguity, or trust risk.

Selection Input Why It Matters Agent Rule
Case scope Raw-card condition, sealed authenticity, route failure, and fraud are different expertise domains. Reject arbiters outside signed scope unless both humans explicitly waive.
Value band A $60 raw card should not require the same process as a $4,000 trophy card. Match fee, response burden, and evidence floor to value at risk.
Evidence floor The arbiter's minimum packet determines seller attention and buyer claim quality. Prefer the lowest evidence floor that still protects the covered promises.
Fee and SLA Resolution cost and time are real cost-field components. Rank by expected dispute cost, not headline fee alone.
Conflicts Shops, dealers, graders, communities, and marketplaces have overlapping relationships. Require signed conflict disclosure and human interrupt for material conflicts.
Outcome history Authority hardens only when rulings later match evidence and settlement outcomes. Weight history by category, value band, route, and ruling type, not one global score.
Agent delegation Arbiter agents make small cases scalable but can hide accountability if unbounded. Accept delegated rulings only within signed scope, value, remedy, and escalation limits.
Automation band Cheap transactions need resolution without human fees swallowing the trade. Allow automated rulings only when selected pre-lock, under value cap, and inside deterministic remedy scope.
Friction thresholds The moment uncertainty becomes meaningful, automation becomes a risk rather than a savings. Pause or escalate on high value, unclear evidence, fraud/authenticity, material conflicts, privacy exposure, or severe remedy.
Replacement set Disputes should not strand funds if the chosen arbiter disappears. Pre-commit backups where possible; emergency handoff requires timeout and replacement acceptance.

Resolution

Every ending is promised, happened, accepted.

Resolution should compare what was promised, what actually happened, and who accepted which exception. This avoids vibes and gives agents a crisp packet for claims or arbitration.

Promised

Condition band, item claim, evidence tier, route, insurance, signature, inspection, bond scope.

Happened

Carrier events, handoff memo, verifier note, received evidence, buyer confirmation, exceptions.

Accepted

Explicit waivers, underinsurance approval, route changes, inspection acceptance, human prompts.

Case Type Required Grounds Possible Remedy Abuse Control
wrong_item Received evidence conflicts with inventory claim. Refund, return route, seller bond action, reputation event. Requires received-item packet and inventory packet.
material_misdescription Condition, authenticity, completeness, or serial claim materially differs. Partial refund, return, verifier review, proportional bond action. Requires specific promise and specific contrary evidence.
partial_delivery Some but not all items or components arrived. Proportional refund, replacement shipment, partial bond action. Requires manifest, package evidence, and received-count evidence.
route_failure Seller changed route, underinsured, failed signature, failed packaging, or missed handoff. Claim packet, seller-owned gap, bond action, refund path. Requires route promise and route event evidence.
non_shipment No valid acceptance scan, handoff memo, verifier intake, or proof of route start. Refund, seller bond action, reputation event. Seller can cure before timeout by attaching route evidence.
buyer_remorse Buyer wants out without covered failure. Only remedies explicitly allowed by return terms. Excluded from seller bond unless terms say otherwise.
frivolous_dispute Dispute lacks grounds, packet, or material contradiction. Dispute bond forfeited, seller payout released, buyer reputation event. Disputing party posts cost bond above configured value/risk thresholds.

API surface

The first API can be small.

Keep the alpha API focused on posting intents, inventory, proofs, candidates, evidence, route events, and resolution packets.

Local EVM harness

Anvil tests the money rail without dragging the whole protocol on-chain.

The first runnable contract lives in /Users/che/Marketplace/chain. It now deploys an actor registry, a predicate-verifier stub, and escrow. The registry proves buyer, seller, verifier, arbiter, and verifier-contract authority; escrow anchors the money, bond, packet hashes, route, inspection, claim, and settlement gates. The cost field, item fingerprints, photos, scans, claim packets, and agent traces stay off-chain as signed objects.

On-chain now

  • Native ETH escrow and seller bond.
  • Optional buyer dispute bond for abuse control.
  • Registered buyer, seller, verifier, and arbiter controller addresses.
  • Verifier, arbiter, and predicate-verifier authority records.
  • Intent, terms, proof, evidence, route, claim, ruling, and receipt hashes.
  • Seller- or verifier-signed item fingerprints before inventory reservation.
  • Buyer-scoped verifier approval before verifier-committed fingerprints.
  • Buyer-scoped verifier approvals before verifier attestations can be anchored.
  • Verifier attestation commits bound to subject hash, scope-set hash, and method-id hash.
  • Seller-signed inventory locks bound to the committed item fingerprint.
  • Buyer-opened fingerprint challenges that block route commitment until cleared.
  • Attestation-bound fingerprint challenge clearance for verifier-cured evidence.
  • Route commitment consumes a cited spendability packet hash and validates a typed route assembly witness before the route can lock.
  • Active item-fingerprint collision checks across open trades.
  • Active inventory-lock collision checks across open trades.
  • Replay rejection for duplicate packet hashes inside a trade.
  • State transitions for delivery, inspection, claim, resolution, and settlement.

Off-chain by design

  • Human-readable cost-field objects and agent mandates.
  • Photos, scans, videos, shipping pages, handoff memos, and insurance packets.
  • Marketplace reputation proofs and trust-decision traces.

  • Delegated agent policy, key rotation, and long-lived reputation weighting.

Signature layer

Every packet in the local probe is canonical JSON, hashed with keccak, and signed by the registered actor controller using Ethereum personal-sign semantics. Escrow now requires those signatures before accepting packet hashes that move trade state: intent, terms, proof, evidence, route, claim, ruling, receipt, cancellation, and arbiter replacement. Once a packet hash is anchored for a trade, replaying it as another proof or evidence packet is rejected.

Authority gates

Escrow refuses trades with unknown buyers, unknown sellers, or inactive arbiters. Registered verifiers cannot attach loose evidence; they can only commit a scoped attestation after buyer approval, and that attestation must bind to an anchored subject, scope set, and method. Private predicates must pass a registry-approved verifier contract. If an arbiter is revoked mid-claim, buyer and seller can still co-sign a replacement; if one side stalls, a one-party proposal opens only after timeout and replacement-arbiter acceptance.

ItemFingerprint before InventoryLock

The newest primitive separates object identity from inventory reservation. An ItemFingerprint can be a raw-card photo set, a slab cert correlation, a shop-verifier note, a marketplace proof chain, or a later privacy-preserving predicate. The contract enforces the signed hash, active-collision rule, buyer-scoped verifier approval, scoped verifier attestation, typed inventory-lock binding, buyer challenge gate, and attestation-bound challenge clearance; agents, verifiers, and arbiters still judge whether the evidence is strong enough for the buyer aperture.

Spendability is a real gate

Evidence can now be durable memory without automatically becoming action. A seller route must cite a nonzero EvidenceSpendability packet hash and the contract-derived RouteAssemblyWitness for that escrow, chain, trade, route, spendability hash, wall bundle, assembly history, item fingerprint, inventory lock, and gate. Escrow consumes the spendability hash and stores the typed assembly witness before route lock. The full packet semantics are still checked off-chain, but a spendability packet that does not inherit the current assembly provenance blocks in the harness before route lock.

Invariants

Rules that should not break.

These are the checks a simulation, implementation, or verifier should enforce before trusting a trade path.

No unverifiable signature

Every signed object must resolve to an active ActorRecord key and canonical payload.

No scalar trust collapse

Trust sources must retain source, scope, freshness, issuer, and claim.

No release without a gate

Escrow cannot release unless the specified release gate is satisfied or explicitly waived.

No route without spendability

Route commitment must cite assembly provenance, consume a spendability packet hash, and pass the contract-derived route assembly witness; evidence alone cannot spend.

No access by resemblance

A source can look right, a coordinate can be visible, and a seller can seem trustworthy; none of that can act unless the assembly history names the provenance path for this gate.

No untyped object

Inventory cannot be reserved until a signed item fingerprint defines the physical thing at stake.

No challenged route

A seller cannot commit route while the buyer has an active fingerprint challenge on the trade.

No silent semantic collision

Same cert, stale photo, mixed-front/back, or same-card alias signals must become a challenge, waiver, or verifier cure packet before route.

No stray verifier

A verifier cannot attach loose evidence or commit item identity or review unless the buyer scopes that verifier to the trade.

No scope laundering

A verifier attestation cannot be displayed or used without its anchored subject, method, checked scopes, exclusions, freshness, and challenge path.

No unbound proof

A proof cannot satisfy a release gate unless bound to the trade id or challenge nonce.

No hidden underinsurance

The owner of any value gap must be typed before route commitment.

No hidden bond gap

Bond coverage must be disclosed as amount and fraction of item value before escrow lock.

No route mutation

Seller-side route changes after escrow require buyer-side acceptance.

No vague bond

Bond scope must define covered promises, exclusions, adjudicator, and payout path.

No undefined arbiter

Arbiters must be registry-listed, profile-signed, conflict-disclosed, and accepted in terms before they move money.

No unbounded arbiter agent

Arbiter agents need signed delegation with scope, value, remedy, escalation, and expiry limits.

No frictionless ambiguity

Automated arbitration must stop when value, remedy severity, evidence ambiguity, trust gap, privacy exposure, conflict risk, or attention cost crosses threshold.

No invisible AI ruling

Automated rulings must be replayable from signed terms, evidence packets, remedy schedules, and engine version.

No random replacement

Replacement arbiters must come from the accepted set or satisfy timeout, inactive-arbiter, and acceptance gates.

No free dispute griefing

Disputes require grounds, packet hash, requested remedy, and cost controls when risk warrants.

No all-or-nothing failure

Partial delivery and partial misdescription must support proportional remedies.

No missing packet

Clean close, claim, dispute, verifier mismatch, and refund must all produce a packet.
